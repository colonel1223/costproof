The central result

Rows two and three have identical point estimates. Same number, same data, same model. Only the standard error differs. That moves coverage from 23% to 91% and cuts false positives from 83% to 13%.

The lesson generalises well beyond cloud cost: the estimate was never the problem — the uncertainty around it was. A method can be nearly unbiased and still be useless for decisions, because a confidence interval that only contains the truth a quarter of the time will approve almost anything.

Why 100% power is a red flag, not a win

The naive method detects a real effect every single time. It also detects an effect when there isn't one, four times in five. A test that always says yes has perfect power and no information content. Synthetic control is the mirror image: it never raises a false alarm, but it only catches half the real effects. Permutation DiD is the only row that is honest in both directions at once.

The waste classifier, at the operating points an analyst actually sees

Trained on 280 resources, tested on 120 the model has never seen — 61,440 held-out resource-days at 5.2% waste prevalence. The comparison row is the threshold rule most FinOps tools ship with: flag anything above 2× its 28-day average.

ROC AUC is 0.648 and PR AUC 0.174 against a 0.052 prevalence baseline — 3.3× lift. Both are reported in the output rather than buried, because the honest reading is that the model ranks the top of the queue extremely well and the middle poorly. Only the top is actionable, and the report says so.

Why this framing beats a headline accuracy number

At 5.2% prevalence, a model that predicts "no waste" for everything is 94.8% accurate and worth nothing. Precision@k answers the question the business actually has — if I give an analyst ten things to look at tomorrow, how many are real? — and it is the metric that makes the baseline comparison damning: the threshold rule raises 318 alerts to find 2.8% of the problem.

The estimator, checked by a second language

A hand-rolled estimator carries an obligation: prove it against a reference implementation that shares nothing with it. Every one of the 117 panels was exported and re-estimated in R three ways — plm::plm (the canonical panel-econometrics package, same within transformation), a brute-force lm() with 178 explicit dummies, and sandwich::vcovCL for the clustered standard error.

03 What we actually did, step by step

Step 1 — Created a repository on GitHub

Goal: get the project a public web address. A project on your laptop is invisible; nobody can look at it.

git config user.name "Spencer Cottrell"
git config user.email "261395650+colonel1223@users.noreply.github.com"
git branch -M main
gh repo create colonel1223/costproof --public

Why the email mattered: git stamps an email on every commit, and GitHub uses only that to decide whose work it is. Wrong email → the commit shows as an anonymous ghost and doesn't count on your profile. The @users.noreply address is GitHub's relay: it attributes correctly without exposing your real address in a permanent public record.

Step 2 — First commit and push

git add -A          # pick the files
git commit -m "..." # package them into a snapshot
git remote add origin https://github.com/colonel1223/costproof.git
git push -u origin main   # send it

The one error you hit: index.lock: File exists. Git writes a lock file while it's mid-operation and deletes it when done. A crashed or interrupted git process leaves it behind, blocking everything after. rm -f .git/index.lock clears it. Safe — it's a temp file, never your work.

Step 3 — Installed the package and generated the data

pip install -e ".[dev]"      # install, in editable mode
python -m costproof.cli data # run the simulator

Produced 216,036 rows across five files. data/bronze/ holds the raw billing feed; data/gold/ holds the supporting tables.

Step 4 — Looked at one row

The single most useful thing so far. One row of the billing feed says: on 1 Jan 2025, resource r-0000 — owned by the search team, running in Ireland — consumed 119 machine-hours at $0.384/hour, listing at $45.72 and costing $42.06 after discount.

216,036 rows = 400 resources × 540 days. Eighteen months of an $8.9M/year cloud bill.

Step 5 — Built the silver layer in SQL

sql/silver_billing.sql, 145 lines. Bronze is the raw feed and never gets edited. Silver is where the feed becomes analysable:

  • COALESCE(Tags['business_unit'], 'unallocated') — turn a missing tag into an explicit category rather than a null that silently drops rows out of every GROUP BY.
  • An is_tagged boolean, so "how much can't we attribute" is one WHERE clause away.
  • Derived savings measures — the gap between list, contracted and effective cost — computed once here instead of re-derived differently in five downstream queries.

The design principle: a decision made once in the silver layer is a decision the whole project agrees on. A decision made ad hoc in each query is five decisions that will eventually disagree.

Step 6 — Built the gold layer: unit economics

sql/gold_unit_economics.sql, 120 lines of common table expressions joining spend to business drivers on 28-day trailing windows.

The result answers the question the invoice can't: every business unit's bill went up — which of them is actually a problem? Four of the five were spending more per month while spending less per unit of output. That's growth. One, bu-datasci, was spending more per unit. That's the only real regression, and on the invoice alone it looks identical to the other four.

The join is an INNER JOIN, which deliberately drops unallocated and bu-platform: neither has a business driver, so a unit cost for them would have a fabricated denominator. That exclusion is reported as a caveat rather than left for a reader to discover.

Step 7 — Waste detection with a classifier

src/costproof/ml/waste.py, 315 lines. A gradient-boosted classifier over nine relative features — cost drift versus the resource's own baseline, coefficient of variation, weekend-to-weekday ratio.

Relative, not absolute, and that is the whole trick. Train on absolute dollars and the model learns "expensive resources are wasteful," which is not a finding, it's a restatement of the price list. Train on each resource's deviation from its own history and it learns what an idle machine's cost profile looks like regardless of size.

The evaluation split is by resource, not by row. Split by row and the same machine appears in both training and test, the model memorises it, and the score is meaningless. That is data leakage, and it is the most common way a model reports 97% accuracy and then fails in production.

Step 8 — The validation harness

src/costproof/causal/validate.py. Runs all four estimators over all 117 interventions and scores each against the simulator's known truth. This is the file that produced the table in section 02, and it is the reason the project can make claims instead of assertions.

Step 9 — A retrieval layer over the runbooks

Three knowledge documents — a remediation runbook, a measurement policy, a pricing reference — chunked on markdown headings into 22 passages. Retrieval is TF-IDF over word 1–2 grams and character 4–5 grams, with a relevance floor below which nothing is returned at all.

The character n-grams exist because cloud vocabulary is full of near-misses: rightsizing / right-sizing, p4d.24xlarge / p4d. Word-level matching treats those as unrelated tokens; character-level matching sees the overlap.

Step 10 — The agent, its tools, and its gates

src/costproof/agent/. A tool registry where each tool declares a JSON schema, returns a structured ToolResult carrying its own method description and caveats, and gets logged with arguments and elapsed time.

Findings pass through a governance gate: anything above $1,000/year, or anything that would delete or modify a resource, is marked as requiring human approval and is not executed. Three of four findings in the last run were gated. The audit record is written to outputs/audit/ as JSON with the run ID, backend, Python version, platform, every tool call and every retrieved source.

Step 11 — watsonx, and the reason it degrades gracefully

llm.py defines two backends behind one interface: WatsonxBackend calling ibm/granite-3-8b-instruct with greedy decoding, and DeterministicBackend, which needs no credentials at all.

Why the fallback matters

The fallback isn't a convenience. Because the offline backend produces every number in the report, it is a standing proof that no number depends on the language model. The model narrates; it never calculates. If the fallback couldn't reproduce the figures, that would be evidence the model was doing arithmetic somewhere it shouldn't.

check.py is a six-stage credential checker, written because the three common watsonx failures all produce error messages that name the wrong cause — a missing service association returns a permission error that never mentions the association, a region mismatch looks like bad credentials, and a space ID passed where a project ID belongs returns a not-found rather than a type error.

Step 12 — The report

python -m costproof.cli review produces reports/cost-review.md: four findings, each with its dollar impact, the method used to measure it, the recommended action, the risk of taking that action, and its caveats — plus a governance summary, the full tool-call log with timings, and every source retrieved.

Step 13 — The CFO business case in Excel

scripts/build_business_case.py generates a five-sheet workbook: assumptions, the value model, measurement accuracy, sensitivity, and a summary. 99 formulas, zero formula errors, blue for inputs and black for formulas so a finance reader can see at a glance which cells are assumptions.

Five-year NPV $557,508 at a 12% discount rate, benefit-to-cost ratio 6.27×. Actions measured rise from 79 to 138 per year; avoided wasted effort rises from $140,986 to $246,279; net cash flow from $81,546 to $226,839.

The deliberate omission

The $115,746 of annual misstatement reduction is shown on the sheet and excluded from the NPV. Reporting a number more accurately does not by itself produce cash, and a business case that books accounting accuracy as savings is the kind of thing a CFO stops reading. Leaving it out and saying why is worth more than the $115,746 would have added.

Step 14 — The MCP server

src/costproof/agent/mcp_server.py. The Model Context Protocol is an open standard for connecting a language model to tools, data and prompts over one interface — to model-tool integration what ODBC was to databases. Your server exposes all three primitives: 6 tools read live from TOOL_REGISTRY, 6 resources (the three runbooks, the latest report, the two validation tables), and 1 prompt carrying the operating rules.

Five design decisions, each defensible:

  • Low-level Server, not the high-level class. The high-level class derives schemas from Python type hints, which would mean a second definition of every tool. The low-level API reads the registry at request time — one statement of what the agent may do.
  • Every tool annotated read-only. read_only_hint=True, destructive_hint=False, idempotent_hint=True, open_world_hint=False. Honest capability declaration is what lets a client auto-approve safely.
  • Schema validation before dispatch. Every call is checked against the tool's JSON Schema. find_waste(top_n="ten") is rejected with 'ten' is not of type 'integer' and never runs — so it never reaches the audit log, because nothing happened.
  • Provenance and governance travel with every result. Method, caveats, sources, and a governance block applying the same $1,000/yr gate as the in-process review.
  • Two kinds of "no", kept distinct. Unknown tool or bad arguments → isError: true. Tool ran and concluded "this estimate is not causal" → isError: false, ok: false. A refused savings claim is the system working, not a malfunction to retry.

Eight tests launch the real server as a subprocess and speak the protocol to it over stdio — handshake, capability advertisement, schema rejection, provenance, the two kinds of no, resources, prompt. And it's wired into Claude Desktop: ask it about your untagged spend and it calls your code on your data.

Step 15 — The SDK broke underneath us, and we shipped red

My environment had resolved mcp 1.27; your pip install got 2.2.0. Between them the low-level API changed shape entirely: handlers moved from decorators to constructor injection, field names went snake_case, and the SDK stopped validating tool inputs for you. The server passed 8 tests here and crashed on import on your Mac — and you committed and pushed with 8 failures showing.

The port took one careful read of the v2 source. The lesson is in the bugs section below, and it changed pyproject.toml: mcp>=1.0 became mcp>=2.0.

Step 16 — R cross-validation

src/costproof/causal/crossval.py rebuilds every study panel exactly as run_study does and writes them to one CSV — 660,756 resource-days — with Python's coefficient and clustered SE for each. R/crossvalidate.R reads it and re-estimates every panel with plm, with lm() plus explicit dummies, and with sandwich::vcovCL. python -m costproof.cli crossval runs the whole thing and writes reports/r-crossvalidation.md with all 117 rows side by side.

CSV rather than Parquet on purpose: the point of a cross-validation is a second implementation with as few shared dependencies as possible, and Parquet would have made R depend on Arrow. A CSV depends on nothing.

The one subtlety worth owning: plm's own clustered SE came out 1.5% smaller than Python's. Not a bug — a convention. The small-sample correction is G/(G−1) × (N−1)/(N−K), and plm counts K as 1 (just the slope) while Python counts 178 (slope plus every absorbed fixed effect). sandwich::vcovCL(type="HC1") uses Python's convention and matches to eight digits. Knowing which convention a package uses is the difference between reporting a standard error and defending one.

Step 17 — Hardening

The standard was no errors. Anyone who runs ruff check and sees 19 findings, or pytest and sees 430 warnings, doesn't read further.

  • 19 → 0 lint findings. Lambdas assigned to names became defs; four functions calling PanelSpec() in a default argument now resolve it in the body; semicolon-joined statements split; zip() made strict=True; unused imports removed.
  • 430 → 0 test warnings. One line in the generator — dates + pd.Timedelta(days=1) — tripped a NumPy 2.5 deprecation inside pandas 2.3. Replaced with explicit-unit numpy arithmetic. Proven a no-op by generating the estate with old and new code side by side: every column identical.
  • python -m costproof.cli warehouse. A real warehouse/ package that runs the SQL layers in order, replacing two python -c one-liners. Ran it twice and hashed the output: byte-identical. That's idempotence demonstrated, not asserted.
  • Removed the empty econ/ package. An empty module in a public repo reads as scaffolding nobody finished.

04 Thirteen bugs, and what each one taught

Keep these. They are the difference between a project you built and a project you can talk about. Every one of them was found by checking output against something known, not by reading code.

1. Untagged spend reported as 0.0%

The tagging check used if value is not None. Pandas represents a missing value as NaN, and NaN is not None evaluates to True — so every missing tag counted as present. Fixed with isinstance(v, str).

Lesson: a result of exactly zero is a bug until proven otherwise. Real data is never that clean.

2. AI/ML showed as 63% of all spend

Quantity was being derived from the pricing unit, so a p4d.24xlarge at $32.77/hour swamped everything else in the simulated estate. Fixed by giving every SKU an explicit base_units_per_day.

Lesson: when one category dominates implausibly, check the generating mechanism before you check the analysis. Also — the first fix attempted was a regex patch whose non-greedy match spanned multiple entries and would have corrupted the file. Structural edits belong in structural tools.

3. The naive estimator's bias had the wrong sign

The whole premise is that before/after overstates savings. The first simulator produced a bias of +0.106 in the wrong direction — the naive method was understating. That meant the simulated world didn't contain the phenomenon the project exists to correct.

Six changes fixed it: waste made persistent rather than transient; interventions made to terminate that persistence; the AR(1) persistence parameter raised from 0.72 to 0.90; a two-pool assignment separating genuinely-remediated resources from noise; the waste-free pool made to exclude all waste rather than just the targeted kind; and the intervention trigger switched to a 120-day rolling baseline.

Lesson: the bug was diagnosed by plotting the average spend profile around the intervention date and seeing it already at −0.37 fifteen days before treatment. Plot the thing before you theorise about it.

4. DiD confidence intervals covered the truth 23% of the time

Cluster-robust standard errors are asymptotic in the number of clusters. With one treated unit there is no asymptotic regime, and the formula returns a number that looks like a standard error and isn't one. Replaced with permutation inference — re-randomise the treatment assignment thousands of times and read the p-value off the resulting distribution. Coverage went to 91%.

Lesson: a standard error is a claim about a sampling distribution. If the assumptions behind that distribution don't hold, the number is arithmetic without meaning.

5. The parallel-trends test rejected 98.3% of cases

It was built on the same broken standard errors. Rebuilt on randomization inference. Now 88% of interventions pass, and the estimates that pass have 95.1% coverage — which is what a filter is supposed to do: not improve every estimate, but tell you which ones to trust.

Lesson: when a diagnostic fires on almost everything, suspect the diagnostic.

6. The first full run gave 7% coverage across every method at once

The analysis used an 84-day pre-treatment window while the simulator's detection lag was 20–75 days — so the "before" period contained the waste the intervention was about to fix, plus the period where it was already being noticed. Every method was estimating against a contaminated baseline.

Lesson, and the one to remember: when every method fails together, suspect the data specification, not the methods. Independent methods do not share a bug; they share an input.

7. A $2.58M phantom saving on the untagged bucket

Commitment purchase rows have a ContractedCost − EffectiveCost gap that is meaningless — it's the prepayment, not a discount. Summing it produced $2.58M of savings that never existed. Fixed by guarding every savings measure with CASE WHEN ChargeCategory = 'Usage'.

Lesson: an arithmetic operation being valid on a column doesn't mean it's meaningful for every row in it.

8. The Excel model had zero formula errors and wrong numbers — three times

Row references like $B$11 were hardcoded into sheets whose rows are generated dynamically. Everything evaluated cleanly; analyst time read −$4,752,000 instead of −$15,840. Fixed by having each sheet-building function return a label-to-cell map, so downstream formulas ask for "the cell holding analyst hourly rate" rather than "B11".

Lesson: a clean recalculation proves your formulas evaluate. It says nothing about whether they point at the right cells. Check two or three values by hand before building out a grid.

9. IRR came back as n/a and payback as −0.4 years

Not a bug — the project is cash-positive in year one, so the cash-flow series never changes sign and IRR is mathematically undefined. Replaced with a benefit-to-cost ratio of 6.27× plus a note explaining why IRR is absent.

Lesson: knowing when a standard metric doesn't apply is worth more than producing it anyway. A finance reader will notice either way.

10. The MCP SDK changed its API between my machine and yours

pyproject.toml said mcp>=1.0 — "anything from 1.0 up is fine." That was true until 2.0 shipped with a different handler API. My environment had 1.27; your pip install got 2.2.0; the server crashed on import; all 8 protocol tests failed with Connection closed — a message that says nothing. The captured stderr of the subprocess said everything: 'Server' object has no attribute 'list_tools'.

Lesson: a major version number is a promise that things changed incompatibly. Pin the major of anything whose API you call directly. And when a client error is generic, go read the server's own log — the useful message is always on the side that actually broke.

11. You committed with 8 red tests

The commit went through because git doesn't care whether tests pass. For twenty minutes the public repository showed 8 failures to anyone who cloned it.

Lesson: the commit command comes after the green test run, never in the same paste. A pre-push hook that runs pytest would make this impossible; for now the rule is procedural.

12. Unknown tool returned isError: false

The first server treated "tool doesn't exist" the same as "tool ran and said no" — a normal response with ok: false inside. A test caught it. The fix drew the line the whole governance model rests on: the request failing is a protocol error; the tool concluding "this estimate is not causal" is a successful result that happens to be a refusal.

Lesson: collapsing those two would teach a client that a refused savings claim is a malfunction to retry — precisely backwards. Write the test for the distinction, not just for the happy path.

13. Two Pythons, and source ~/.zshrc switched which one won

Your Mac has pyenv (3.11) and miniconda (3.13). CostProof lives in miniconda's. After re-sourcing your shell config, pyenv's shims jumped ahead on PATH, so python and pip silently became 3.11 — no costproof, no mcp — while pytest (which pyenv doesn't have) still ran under 3.13. That's how you got 1 skipped: the MCP tests skip themselves when the SDK isn't importable. Fixed with pyenv local system, which tells the shim to step aside inside this project.

Lesson: python and pip can be different interpreters. Always python -m pip. And when a test suite reports skipped rather than passed, the green isn't real.

Two more, about reproducibility

A pandas FutureWarning couldn't be reproduced in the cloud environment because it runs pandas 3.0.2 and your Mac runs 2.3.3 — downgraded because ibm-watsonx-ai pins pandas<2.4.0. The first diagnosis ("empty frame") was wrong; the real cause was all-NA columns in a concat. A dependency you didn't choose can pin a version you didn't notice, and version drift between two machines is a real and ordinary source of "works on mine."

And after the timedelta fix, the regenerated Parquet file's checksum changed. First instinct: the fix altered the data. It hadn't — the previous file simply predated an earlier fix. Proven by generating with both versions of the line and comparing every column, and by writing the same frame twice to confirm Parquet itself is deterministic. Bit-identical and value-identical are different claims. When a checksum moves, find out what moved before concluding anything.

05 Terms — the command line

Terminal a.k.a. console
The window where you type commands instead of clicking. Just a place to work — it isn't a language or a tool itself.
Shell zsh, bash
The program running inside the terminal that reads what you type and runs it. macOS defaults to zsh. Terminal is the window; shell is the thing listening.
CLI command-line interface
Any program you drive by typing rather than clicking. git is a CLI. python -m costproof.cli is the CLI we built for this project.
Directory
A folder. cd = change directory, ls = list contents, pwd = print working directory (where am I).
Path
A file's address. ~ means your home folder, so ~/Projects/costproof is /Users/spencer/Projects/costproof. A leading . (like .git) means hidden — ls won't show it unless you pass -a.
Flag option, switch
A modifier after a command. In git add -A, the -A is a flag meaning "all files." In ls -lh: l = long format, h = human-readable sizes.
Environment variable
A named value the shell hands to every program it starts. Credentials live here rather than in code, which is why WATSONX_API_KEY is read from the environment and never appears in a source file.
.env file
A local file of KEY=value lines, loaded into the environment at startup and listed in .gitignore so it is never committed. A credential is safe in exactly two places: this file, and the provider's own console.
(base) in your prompt
Tells you which Python environment is active. You're in Anaconda's default, called base.

06 Terms — git and GitHub

The distinction people get wrong

Git is a program on your laptop that tracks changes to files. GitHub is a website that stores copies of git projects online. They are different things by different companies. Git works fine with no internet; GitHub is where you put it so others can see it.

Repository repo
A project folder that git is tracking. The tracking data lives in a hidden .git subfolder — delete that and it's just a normal folder again.
Commit
A saved snapshot of your files at one moment, with a message explaining why. Your history is a chain of commits. Think "save point," not "save."
Staging area the index
A holding pen between your files and a commit. git add puts files in it; git commit packages whatever's in it. This is what lets you make five changes and commit only three, so your history reads as decisions rather than noise.
Tracked / untracked
Tracked = git is watching this file. Untracked = git can see it but ignores changes. In git status, ?? = untracked, A = staged as new, M = modified.
.gitignore
A file listing patterns git should never track. We ignore data/ and __pycache__/ because they're generated from code — committing them creates two sources of truth that can silently disagree.
Re-including a file inside an ignored folder
A rule that caught us: git never descends into an ignored directory, so outputs/ followed by !outputs/figures/*.png does nothing. You have to un-ignore each level on the way down — outputs/*, !outputs/figures/, outputs/figures/*, !outputs/figures/*.png.
Branch
An independent line of commits. main is the default. Branches let you work on something risky without touching the working version.
Remote origin
A nickname for a URL where a copy of the repo lives. origin is the convention for "the main one." git remote add origin <url> only records the address — it uploads nothing.
Push / pull / clone
Push = send your commits up. Pull = fetch changes down. Clone = download a whole repo for the first time.
gh
GitHub's official CLI. Does things over the website's API that plain git can't — like creating a repository.

07 Terms — Python and packaging

Package
A folder of Python files meant to be imported as a unit. Ours is src/costproof/, so import costproof works anywhere.
Module
A single .py file. costproof/causal/did.py is the did module inside the causal subpackage.
Dependency
Another package yours needs to run. Ours are listed in pyproject.toml: pandas, numpy, scikit-learn, statsmodels, duckdb, pyarrow, matplotlib, openpyxl.
Version pin
A constraint like pandas<2.4.0 that a dependency imposes on your environment. Installing ibm-watsonx-ai silently downgraded pandas on your Mac. Pins are transitive and mostly invisible until something behaves differently on two machines.
pyproject.toml
The project's config file: name, version, dependencies, tool settings. The modern standard, replacing the older setup.py.
Editable install pip install -e
Installs a link to your source folder rather than a copy. Edit a file and the change takes effect immediately — no reinstall. Standard while developing.
Virtual environment venv, conda env
An isolated Python with its own packages, so project A needing pandas 1.x doesn't break project B needing 2.x. Your (base) is Anaconda's default one.
__init__.py
A file that marks a folder as an importable package. Often empty — its presence is the point.
Type hints and Protocol
Annotations describing what a function takes and returns. A Protocol defines an interface by shape rather than inheritance: Backend says "anything with a generate() method qualifies," which is how watsonx and the deterministic fallback are interchangeable without either knowing about the other.
python -m <name>
Run a package as a program. python -m costproof.cli data runs our CLI with the argument data.

08 Terms — cloud computing

Cloud provider AWS, Azure, GCP
A company renting computers by the hour. Amazon Web Services, Microsoft Azure, Google Cloud Platform. You never see the hardware; you rent capacity.
VM virtual machine, instance
A software-simulated computer running on the provider's hardware. One physical server is carved into many VMs. Standard_D8s_v5 in your data is an Azure VM size: 8 virtual CPUs and a fixed amount of memory.
Instance type / SKU
The specific configuration you rented — CPU count, memory, whether it has a GPU. m6i.xlarge is a general-purpose AWS VM; p4d.24xlarge is a GPU machine at $32.77/hour.
Region and availability zone
Region = the geographic datacentre cluster (eu-west-1 is Ireland). Availability zone = an isolated datacentre within it. Prices differ by region.
Provisioning
Requesting resources. Over-provisioned = you rented more than you use, and pay for all of it. That's the single most common form of cloud waste.
Rightsizing
Shrinking an over-provisioned resource to what it actually needs. One of the optimisation actions in your dataset.
Idle / orphaned / zombie
Three flavours of waste. Idle = running but doing nothing. Orphaned = the thing that used it is gone, but it still bills (a disk whose VM was deleted). Zombie = a whole test environment nobody turned off. None of them self-resolve; they bill until a human kills them.
Autoscaling
Automatically adding capacity under load and removing it after. Reduces waste, but makes cost analysis harder because capacity is a moving target.
IaaS / PaaS / SaaS
Rent raw machines (Infrastructure), rent a managed platform (Platform), or rent finished software (Software). Cloud waste statistics usually refer to IaaS and PaaS.

09 Terms — cloud finance (FinOps)

FinOps
The practice of managing cloud spend — the discipline that exists because cloud turned a predictable capital purchase into a variable bill any engineer can increase at 3am without asking anyone.
FOCUS
FinOps Open Cost and Usage Specification. An open standard defining how billing data should be structured, so AWS, Azure and GCP bills can be compared without custom translation for each. Your data conforms to FOCUS 1.2 — which is why this project would work against real exports unchanged.
The four cost columns
ListCost = sticker price. ContractedCost = after the company's negotiated discount. EffectiveCost = the true economic cost for that day, spreading prepayments across the period they cover. BilledCost = what actually hit the invoice that day.
Why EffectiveCost is the right one
If a company prepaid for capacity, those days show BilledCost = $0 because the money left months ago. Analyse BilledCost per resource and prepaid resources look free. They aren't. EffectiveCost is what you use for anything economic.
ChargeCategory
FOCUS's field distinguishing Usage rows from Purchase, Tax and Credit rows. Mixing them is how the $2.58M phantom saving happened: a discount calculation that is meaningful on a usage row is nonsense on a purchase row.
Commitment discount Reserved Instance, Savings Plan
Promise to spend a certain amount for 1–3 years, get 25–35% off. The risk is obvious: commit to capacity you stop needing and you pay for it anyway. That's unused commitment — waste that never appears as a resource, so no rightsizing exercise will ever find it. Yours: $165,406/year.
Break-even utilisation
For a commitment at discount d, break-even utilisation is 1 − d. Below that, the unused portion costs more than the discount saves. A 30% discount needs 70% utilisation just to be worth having.
Amortisation
Spreading a large upfront payment across the periods it covers, rather than dumping it all in the month it was paid. Without it, a prepayment looks like a spend spike that no optimisation caused.
Effective Savings Rate ESR
Total actual cost divided by what the same usage would have cost at list price. The single number FinOps teams report upward, and it silently blends real optimisation with negotiated discounts that took no engineering work at all.
Tagging
Labels attached to resources saying who owns them (business_unit, cost_centre, environment). Cloud providers don't require them, so real estates run 20–30% untagged — spend nobody can attribute. Yours is 10.6%, or $1,435,302.
Showback / chargeback
Showback = tell each team what they spent. Chargeback = actually bill their budget. Chargeback changes behaviour; showback mostly doesn't. Both require solving tagging first.
Unit economics
Cost per unit of business output — per transaction, per customer, per AI inference. The denominator is the point: without it, a rising bill could be waste or could be growth and you cannot tell which. Only 49% of organisations measure it.
Anomaly detection
Automated alerting when spend deviates from expectation. Every FinOps tool does this. None of them can tell you whether the fix you applied afterwards actually worked — which is the gap this project fills.
TBM
Technology Business Management. A standard taxonomy for mapping IT spend to business services. Authored by Apptio — the company IBM bought for $4.6B.

10 Terms — data warehousing and SQL

SQL Structured Query Language
The language for asking questions of tabular data. Roughly forty years old, still the single most-requested data skill in job postings.
Table, row, column
A table is a grid. Each row is one record (one resource, one day, one charge). Each column is one field (EffectiveCost, ResourceId).
Schema
The definition of a table's columns and their types. FOCUS is a schema standard.
Parquet
A file format that stores data by column instead of by row. Sum one column across 216,036 rows and it reads only that column, not the whole file — often 10–100× faster than CSV, and much smaller. Your billing feed is 11MB as Parquet.
Columnar storage
The idea behind Parquet. Analytics almost always touches a few columns across many rows, so grouping data by column means less disk read per query.
DuckDB
A database that runs inside your Python process — no server to install or start. It queries Parquet files directly, so you can write SQL against a file on disk with no loading step. Increasingly the default for analytical work on a single machine.
The clauses you'll use constantly
SELECT which columns · FROM which table · WHERE filter rows · GROUP BY one row per category · HAVING filter after grouping · ORDER BY sort · LIMIT cap the rows returned.
Aggregate function
Collapses many rows into one number: SUM(), COUNT(), AVG(), MIN(), MAX(). Almost always paired with GROUP BY.
CTE common table expression, WITH clause
A named intermediate result you can reference later in the same query. Turns one unreadable 120-line query into six named steps. The gold layer is built entirely this way.
Window function OVER (PARTITION BY …)
Computes across a set of rows without collapsing them. A 28-day trailing average per resource, with one output row per input row. This is what makes drift features possible — you need each day's value and its own recent baseline on the same row.
COALESCE and NULL contagion
COALESCE(a, b) returns the first non-null value. It matters because NULL is contagious in SQL: any arithmetic touching a NULL returns NULL, and NULL rows drop out of GROUP BY results silently. Turning missing tags into the literal string 'unallocated' makes the gap visible instead of invisible.
JOIN types
INNER keeps only rows matching on both sides. LEFT keeps everything from the left table, filling nulls where there's no match. Our gold layer uses INNER deliberately so that units with no business driver are excluded rather than given a fabricated denominator — and that exclusion is reported.
Bronze / silver / gold medallion architecture
A standard way to organise a warehouse in layers. Bronze = raw source data, never edited. Silver = cleaned, conformed, joined. Gold = shaped for a specific business question. Keeping bronze untouched means any mistake downstream is recoverable — you rebuild from the raw layer rather than trying to reverse the damage.
Star schema, fact and dimension tables
A fact table holds the measurements (cost, quantity) at some grain — ours is one row per resource per day. Dimension tables hold descriptive attributes (which resource, which team, which date) and are joined onto the fact table. Named for the shape of the diagram: one fact table in the middle, dimensions radiating out. Ours are dim_resource and fact_business_driver.
Grain
What one row of a table represents. Getting this wrong is the most common warehouse design error: join two tables at different grains and you silently multiply your measures. State the grain in a comment at the top of every fact table.
ETL / ELT
Extract, Transform, Load — moving data from source to warehouse. ELT (transform after loading) is now more common, because modern warehouses are fast enough to transform in place. This project is ELT: raw Parquet lands first, SQL transforms it after.
Idempotence
Running the same job twice produces the same result as running it once. Our SQL rebuilds each layer from scratch rather than appending, so a re-run can't double-count. A pipeline that isn't idempotent is a pipeline you can't safely retry.

11 Terms — econometrics and causal inference

This is the intellectual core of the project and the part your economics degree makes you credible on. Everything here is implemented by hand in src/costproof/causal/, not called from a library.

Counterfactual
What would have happened if you hadn't acted. Never observable, always the thing you actually need. The entire project exists to estimate it.
Potential outcomes Rubin causal model
Every unit has two potential outcomes: one if treated, one if not. You only ever observe one of them. The "fundamental problem of causal inference" is that the causal effect is a difference between two numbers, one of which is missing by construction.
ATT average treatment effect on the treated
The average effect among the units that actually got treated — not among everyone. This is the right target here: you want to know whether the fixes you did apply worked, not what would happen if you applied them everywhere.
Selection on the outcome endogenous treatment
Teams don't optimise resources at random. They optimise whatever just spiked. That makes treatment assignment a function of the outcome you're about to measure, which is exactly the condition under which before/after comparison breaks.
Mean reversion regression to the mean
An unusually high reading tends to be followed by a lower one, with no cause needed. Combined with the point above: teams act on spikes, spikes subside on their own, and the naive method hands the team credit for gravity.
Difference-in-differences DiD
Compare the change in the treated unit to the change in an untouched comparison group over the same period. The second subtraction cancels anything that hit both — a price change, a seasonal pattern, a company-wide traffic shift.
Two-way fixed effects TWFE
The regression implementation of DiD: absorb a fixed effect for each unit and each time period, so identification comes only from within-unit variation over time. We implement it by demeaning — subtracting each unit's mean and each period's mean — which is algebraically identical to including the dummies and far cheaper. Validated against statsmodels to 1×10⁻¹⁶.
Parallel trends
The assumption DiD rests on: absent the action, treated and control would have moved together. Untestable directly — it's a claim about an unobserved counterfactual — but checkable in the pre-treatment period, which is what an event study does.
Event study
Estimate a separate effect for each period relative to treatment. Pre-treatment coefficients should be flat and near zero; if they trend, the parallel-trends assumption is already failing before the treatment happens.
Synthetic control
Build an artificial comparison unit as a weighted average of untreated units, with weights chosen so the synthetic unit tracks the treated one closely before the intervention. Weights are constrained to be non-negative and sum to one, which prevents extrapolation outside the range of the data.
Placebo test
Run the same method on units that were never treated. Any "effect" you find is noise, and it tells you how big an effect has to be before it means anything. Our synthetic control discards donors whose post-period fit is worse than twice their pre-period fit.
Cluster-robust standard errors
Corrects for the fact that observations within a unit are correlated over time — ignoring this understates uncertainty badly, which is the Bertrand–Duflo–Mullainathan result. But the correction is asymptotic in the number of clusters, and with one treated unit there is no asymptotic regime. That is bug #4 above.
Permutation inference randomization inference
Instead of assuming a sampling distribution, construct one: reassign treatment at random thousands of times, re-estimate each time, and see where the real estimate falls in that distribution. It requires no asymptotics and no distributional assumption, which is why it works with a single treated unit where the formula doesn't.
Coverage
How often a 95% confidence interval actually contains the truth. Should be 95%. The industry method manages 27%; permutation inference gets 91%. This is the single most diagnostic number in the whole project, because it measures whether your uncertainty is honest, not just your estimate.
Bias, RMSE, MAE
Bias = systematically off in one direction, averaged over many estimates. RMSE = typical size of the error, penalising large misses heavily. MAE = typical error, treating all misses equally. A method can have near-zero bias and terrible RMSE if its errors are large and cancel out.
Size and power
Size = how often you find an effect when there is none (false positive rate; should equal your significance level, 5%). Power = how often you find an effect when there is one. They trade off. A method with 100% power and 80% size is not powerful, it is indiscriminate.
Staggered adoption problems
When units are treated at different times, standard TWFE uses already-treated units as controls for later-treated ones, which can produce an estimate with the wrong sign even when every individual effect is positive. Goodman-Bacon decomposes the estimate to show where it comes from; Callaway–Sant'Anna proposes an estimator that avoids the problem. Worth knowing by name — this is live methodological debate.
Conley & Taber (2011)
The canonical reference for inference with a single treated cluster, and the justification for the permutation approach used here. Cite it if asked why you didn't just cluster.
AR(1) process
A series where today's value depends on yesterday's plus noise, with persistence parameter ρ. The simulator uses ρ = 0.90, meaning shocks decay slowly. Persistence is what makes waste look like a level shift rather than a blip, and getting it wrong is what caused bug #3.
Within transformation demeaning
Subtract each unit's mean and each period's mean from every observation, add back the grand mean, then regress. This sweeps out the fixed effects without estimating them. It is what did.py does by hand and what R's plm does inside model = "within".
Frisch–Waugh–Lovell theorem
Partialling a set of regressors out of both sides first, then regressing the residuals, gives the identical coefficient to including those regressors directly. Proven 1933. It is why demeaning and a 178-dummy lm() agree to 7×10⁻¹³ on your panels — and it's the theorem that makes fixed-effects estimation computationally feasible on large panels at all.
Small-sample corrections HC1, sss
Cluster-robust variance is scaled by G/(G−1) × (N−1)/(N−K). The catch is what K counts. sandwich::vcovCL(type = "HC1") and your Python count the absorbed fixed effects in K; plm::vcovHC(type = "sss") counts only the slopes. On your panels that's a 1.5% difference in the SE from the same data and the same model. Neither is wrong; they answer slightly different questions.
plm
R's canonical panel-data package (Croissant & Millo, Journal of Statistical Software, 2008). Fixed effects, random effects, first differences, Hausman tests. The reference implementation your estimator was checked against.
Cross-validation of an estimator
Not the ML sense (train/test folds). Here it means: re-implement the same estimator independently — different code, different language, different author — on the same data, and require the answers to agree. Agreement to machine precision across 117 panels is the strongest correctness claim the project makes.

12 Terms — machine learning

Classification vs. regression
Classification predicts a category (wasteful / not wasteful); regression predicts a number. This project does both, in different places, for different reasons — the classifier prioritises, the regression measures.
Gradient boosting
Fits many small decision trees in sequence, each one correcting the errors of the ensemble so far. Strong on tabular data with mixed feature types, which is most of what finance and operations produce.
Class imbalance
When one outcome is much rarer than the other. Predict "not wasteful" for everything and you can be 95% accurate while being completely useless. Accuracy is the wrong metric the moment classes are imbalanced.
Precision and recall
Precision = of the things you flagged, how many were real. Recall = of the real things, how many did you flag. An investigation queue needs precision, because an analyst's time is the scarce resource; a safety recall needs recall, because a miss is unacceptable.
Precision@k
Precision among the top k ranked items. The right metric when the output is a worklist someone works down from the top. Ours is 100% at k = 10.
ROC AUC vs. PR AUC
ROC AUC measures ranking quality across all thresholds and is flattered by imbalance — it counts true negatives, which are abundant and easy. Precision-recall AUC ignores true negatives and has a baseline equal to the prevalence, so it is the honest one when positives are rare.
Data leakage
Information from the test set reaching the model during training. The subtle version here: splitting rows instead of resources puts the same machine on both sides, the model memorises it, and the reported score is a measure of memory rather than generalisation.
Grouped train/test split
The fix: split by entity, so no resource appears in both sets. The score then answers the question you actually care about — will this work on a machine we've never seen.
Feature engineering
Turning raw columns into inputs a model can learn from. The judgement here is economic, not technical: nine relative features (drift versus own baseline, coefficient of variation, weekend ratio) rather than absolute dollars, so the model learns waste patterns instead of the price list.
Coefficient of variation
Standard deviation divided by mean. A scale-free measure of variability, so a $10/day resource and a $10,000/day resource are comparable. Idle resources have low CV — they cost the same every day regardless of demand.
Feature importance
How much each input contributed to the model's predictions. Useful for explaining the model to a non-technical stakeholder, and for catching leakage — an implausibly dominant feature usually means it encodes the answer.
Prioritisation is not a finding
A model score ranks where to look. It does not establish that anything is wrong. The report states this explicitly for every flagged resource, and the annualised figure is described as the cost those resources carry, not a saving — because what is actually recoverable is unknown until the fix is measured after the fact.

13 Terms — RAG, agents and MCP

RAG retrieval-augmented generation
Retrieve relevant passages from your own documents, then give them to a language model as context. Grounds the answer in specific sources rather than the model's training data, and makes citation possible.
Chunking
Splitting documents into retrievable pieces. We chunk on markdown headings so each chunk is a semantically complete section with a citable name, rather than a fixed number of characters that cuts mid-sentence.
TF-IDF
Term frequency × inverse document frequency. Weights a word by how often it appears in this document and how rare it is across all documents, so common words contribute little and distinctive terms contribute a lot.
n-grams, word and character
Word 1–2 grams capture phrases ("unused commitment"). Character 4–5 grams capture morphological near-misses (rightsizing / right-sizing) that word matching treats as unrelated. Using both is why retrieval hits 100% on corpus-vocabulary questions.
Cosine similarity
The angle between two vectors, ignoring their length. Standard for comparing documents of different sizes, because a long document shouldn't score higher just for being long.
Relevance floor
A minimum score below which nothing is returned. Without it the retriever always returns its top three, however irrelevant, and the model dutifully cites them. Returning nothing is a valid answer.
Recall@k
How often the correct document appears in the top k results. Ours: 85% at k = 3 overall, 100% on corpus-vocabulary phrasing, 62% on paraphrases. Reporting the breakdown rather than the average is what makes it a diagnostic instead of a score.
Lexical vs. semantic retrieval
Lexical matches words; semantic (embedding-based) matches meaning. The 62% paraphrase result is precisely the known weakness of lexical retrieval, and naming it as such — rather than hiding the average — is the point of measuring it.
Grounding and hallucination
A grounded answer is traceable to a retrieved source. The system prompt here forbids stating any figure not present verbatim in tool output, and the architecture backs that up: the deterministic backend proves no figure came from the model in the first place.
Agent
A system that chooses which tools to call, in what order, based on what it finds. Distinct from a pipeline, where the order is fixed in advance.
Tool registry and schema
Each tool declares its name, purpose and parameters as a JSON schema. The schema is the contract: it is what lets a model call a tool correctly without having seen its source, and what lets you validate the call before it runs.
MCP Model Context Protocol
An open standard for exposing tools, resources and prompts to a model over a uniform interface, so the same tool works in any MCP-aware client. The remaining build step is wrapping this project's tool registry as an MCP server.
Governance gate
A rule that stops an agent from acting autonomously past a threshold. Ours: anything over $1,000/year, or anything destructive, requires explicit human approval and is not executed. Three of four findings were gated in the last run.
Audit record
A machine-readable log of what ran: run ID, backend, Python version, platform, every tool call with arguments and timings, every source retrieved. This is what makes an agent's output defensible in a finance context, and what most agent demos don't have.
Graceful degradation
The system does something useful when a dependency is unavailable, instead of failing. Here it is also an architectural proof — see step 11.
Greedy decoding
Always take the highest-probability next token instead of sampling. Makes output reproducible, which matters when the output goes into an audit record.
The three MCP primitives
Tools — functions the model may call. Resources — data the model may read, addressed by URI (costproof://knowledge/…). Prompts — reusable templates with arguments. Most demo servers only do tools; using all three is the difference between a wrapper and an integration.
JSON-RPC 2.0 and stdio
MCP messages are JSON-RPC: a method name, params, and an id to match responses to requests. stdio transport means the client launches the server as a subprocess and talks through stdin/stdout — the standard for local servers, and what Claude Desktop uses. HTTP with server-sent events is the remote alternative.
Handshake initialize
The first exchange: protocol version, server name and version, and capabilities — which primitives the server supports. Your server also sends instructions here, so the "model narrates, never calculates" rule arrives before the client sees a single tool.
Tool annotations
readOnlyHint, destructiveHint, idempotentHint, openWorldHint. Machine-readable claims about what a tool does to the world. A client uses them to decide what's safe to auto-approve. A server that marks a destructive tool read-only has broken the trust model.
Input schema and protocol-level validation
Each tool publishes a JSON Schema for its arguments. Validating against it before dispatch means a malformed call fails at the boundary with a precise message, and the tool's own code never has to defend against bad types.
isError vs ok
isError is the protocol's flag: the request failed. ok is CostProof's: the analysis reached a positive conclusion. A parallel-trends failure is isError: false, ok: false — the request succeeded and the answer is no. Keeping them separate is what stops a client retrying a refusal.
Low-level vs high-level server
The high-level class (MCPServer, formerly FastMCP) derives tool schemas from decorated Python functions — fast to write, but a second definition of every tool. The low-level Server takes handlers you write yourself, so the schema can come from wherever the truth lives. You chose low-level so TOOL_REGISTRY stays the single source of truth.
Structured content
A tool result can carry both human-readable text and a machine-readable JSON object. Yours sends both: the same payload as pretty-printed text for a model to read and as structuredContent for a program to parse.

14 Terms — the business case

NPV net present value
Future cash flows discounted back to today and summed. A dollar next year is worth less than a dollar now, so a stream of benefits has to be discounted before it can be compared to an upfront cost. Positive NPV = worth doing.
Discount rate
The rate used to shrink future cash flows — typically the company's cost of capital. Ours is 12%. It is an assumption, it lives in a labelled blue input cell, and the sensitivity table shows what happens when it moves.
IRR, and when it doesn't exist
The discount rate at which NPV equals zero. Undefined when the cash-flow series never changes sign — which is our case, because the project is cash-positive in year one. Reporting "n/a" with the reason is correct; forcing a number would be wrong.
Benefit-to-cost ratio
Present value of benefits divided by present value of costs. Ours is 6.27×. The right substitute for IRR when IRR is undefined, and easier for a non-finance reader anyway.
Payback period
How long until cumulative cash flow turns positive. Same issue as IRR here — it's immediate, so the metric carries no information.
Sensitivity analysis
Vary the key assumptions and show the range of outcomes. A single NPV is a point estimate of something uncertain; the table is what makes it honest.
Blue inputs, black formulas
Universal financial-modelling convention: blue text = a hardcoded input you can change, black = a calculated cell you shouldn't touch, green = a link to another sheet. A finance reader uses colour to find the levers without reading a single formula.
What to exclude on purpose
Measuring more accurately does not by itself generate cash. The $115,746 of annual misstatement reduction is displayed and deliberately kept out of the NPV. A model that counts accounting accuracy as savings is a model a CFO stops trusting.

15 Terms — engineering hygiene

None of these is glamorous. All of them are what separates a repository someone trusts from one they close.

Semantic versioning semver
MAJOR.MINOR.PATCH. Patch = bug fix, minor = new feature, compatible; major = something changed incompatibly. mcp>=1.0 was a promise to accept any future major version blind. Pin the major of anything whose API you call directly: mcp>=2.0,<3 is the careful form.
PATH and shims
The shell runs the first matching executable it finds walking PATH left to right. pyenv puts a directory of shims — tiny scripts named python, pip — at the front; each shim asks pyenv which version applies (env var, then .python-version in the directory tree, then the global) and forwards to it. system means "step aside." That's what pyenv local system wrote into your project.
python -m pip
Runs pip as a module of this exact interpreter, so what you install goes where python will look. Bare pip can be a different interpreter's pip. This one habit prevents an entire class of "but I installed it."
Idempotence
Running a step twice leaves the same result as running it once. OVERWRITE TRUE in the SQL is what buys it. Proven, not assumed: the warehouse was built twice and the Parquet output hashed identically.
Determinism vs bit-identity
Same inputs → same values is determinism. Same inputs → same bytes on disk is stronger and depends on the file format's metadata. Parquet from pandas is bit-deterministic; not everything is. When a checksum changes, check whether the values did before concluding anything.
Linting ruff
Static analysis that flags patterns known to cause bugs or confuse readers, without running the code. Not all findings are bugs — but zip() without strict=True is a real one (unequal lengths silently truncate), and a reader who sees nineteen findings doesn't check which. Zero is the only number that costs nothing to explain.
Function call in a default argument B008
def f(spec=PanelSpec()) evaluates PanelSpec() once, when the function is defined, and every call shares that object. Harmless for a frozen dataclass, dangerous for anything mutable — the classic def f(items=[]) bug. Idiom: spec=None, then spec = spec or PanelSpec() inside.
Skipped is not passed
A test framework reports skipped when a precondition isn't met. Green with a skip count means part of the suite didn't run. The MCP tests skip when the SDK isn't importable — which is exactly how a wrong interpreter hid a broken server.
git commit --amend and --force-with-lease
Amend rewrites the most recent commit in place instead of adding a new one. --force-with-lease pushes that rewrite but refuses if the remote moved in the meantime — the safe form of force-push. Used to pull .resume.md back out of the public history. For an actual secret you'd rotate it regardless, because rewritten commits can linger in caches.
Case-insensitive filesystems
macOS treats r/ and R/ as the same directory; Linux doesn't. Code that referenced r/ while git recorded R/ worked on your Mac and would have failed on any Linux clone. Fixed to match git. Test on the platform your reviewer uses, not only your own.
